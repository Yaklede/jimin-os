# 회사 계정 연결로 완료 답글 처리

## 사용법

예약 업무를 수정하고 전달할 곳을 Google Chat으로 선택한다. **Chat 완료 답글로 처리하기**를 켜고 프로젝트에 연결된 회사 계정의 대화방을 선택한다. 기존 프로젝트 웹훅 연결은 담당자 Google ID 명단을 확인하는 데 사용한다.

이 옵션을 켠 알림은 **기존 회사 OAuth 계정 이름으로 전송**한다. 별도 Chat 앱, 서비스 계정 키, 회사 Console의 새 앱 등록, 외부 공개 콜백은 필요하지 않다. 옵션을 끈 예약은 기존 웹훅 방식 그대로 전송한다. 이미 운영 중인 예약의 옵션을 자동으로 바꾸지 않는다.

예시:

```text
김경주
- [T-ABCDEF123456] 거래내역 오류 확인 (10월 28일 18:00 마감)

이 알림에 답글:
완료 T-ABCDEF123456
테스트 결과 정상으로 확인했습니다.
```

- 첫 줄은 정확히 `완료 T-번호`, 선택적인 완료 답글은 다음 줄에 적는다.
- OS 일감 번호이므로 ITSM/Redmine 티켓이 없는 일도 처리한다.
- 한 답글에서 한 일의 완료 확인을 요청한다. 여러 일 전체 완료나 일상 문장을 AI로 추측해서 처리하지 않는다.
- 예약 알림의 **답글 스레드**에 남겨야 한다. 대화방 최상위나 다른 스레드의 같은 문장은 처리하지 않는다.
- 현재 담당자로 등록된 Google 사용자 ID만 허용한다. 쉼표로 등록한 복수 담당자를 지원한다. 표시 이름은 권한 근거로 쓰지 않는다.
- 기본 Chat 수집은 1분 주기이며 소스 수·네트워크·재시도에 따라 늦을 수 있다. 즉시 콜백이 아니다.
- 처리 결과는 같은 알림 스레드에 다시 답글로 남긴다.

## 권한 및 동작

기존 연결이 요청하는 `chat.messages.readonly`, `chat.messages.create`를 재사용한다. 실제 승인 권한이 부족하거나 연결이 만료됐으면 기존 회사 계정 연결을 복구해야 한다. 회사의 기존 API 접근 정책을 우회하지 않는다.

예약 실행은 당시의 할 일 ID와 버전을 저장한다. Google의 실제 메시지 이름과 스레드 이름을 저장한 뒤에만 명령을 받는다. 회사 계정·소유자·프로젝트·활성 연결·예약 연결·정확한 스레드·현재 담당자를 대조한다. 새 사용자 로그인이나 담당자별 OS 계정 생성은 요구하지 않는다.

완료된 일을 다시 완료하지 않는다. 일감이 수정되거나 재개돼 버전이 달라졌다면 오래된 알림에서는 처리하지 않고 최신 알림/OS에서 확인하도록 안내한다. 발급한 짧은 번호가 한 알림 안에서 충돌하면 임의의 일을 선택하지 않고 거절한다.

담당자의 답글은 **완료 확인 대기**로 저장한다. 이 단계에서는 일감이 열린 상태이고, CS 완료 답글·Redmine 완료 동기화·완료 웹훅을 예약하지 않는다. 같은 버전의 중복 보고는 한 건으로 묶는다. 확인 대기 중인 일은 담당자 예약 알림에서 제외한다.

소유자의 Mac 알림 피드와 Android FCM 알림에 제목·보고자·홈에서 확인할 안내를 넣는다. 홈의 **완료 확인 대기**에서 완료 메모와 현재 일감 내용을 확인하고 **완료 확인** 또는 사유를 적어 **재작업 요청**을 선택한다. 재작업 요청은 일감을 열린 상태로 유지하고 예약 알림 스레드에 사유를 남긴다.

최종 확인에서만 완료·변경 스트림·원본 CS 완료 답글·기존 ITSM 동기화 대기열·완료 웹훅을 같은 트랜잭션에 저장한다. 원본 대화가 연결돼 있다면 담당자의 완료 메모도 전달한다. 외부 시스템의 전송 성공은 기존 재시도 작업이 별도로 처리한다. 완료 웹훅은 Google Chat·Discord 모두 `일감 제목 · 완료되었어요.` 한 줄이고, 담당자 자동 멘션이나 상세 업무 내용은 붙이지 않는다. 이전에 발송 대기 중이던 상세 완료 이벤트도 전송 시 제목만 사용한다. 배정·변경 웹훅의 상세 내용은 유지한다.

완료 확인은 소유자 인증과 보고 버전·현재 일감 버전을 함께 확인한다. 검토 중 변경되면 최신 내용을 다시 읽어야 하며 자동 승인하지 않는다. 일반 완료 버튼·일감 수정 API·AI의 직접 완료 경로로 확인 대기를 우회할 수 없다. 원본 회사 연결을 지워도 완료 보고 기록은 보존한다.

Mac 알림은 앱이 실행 중인 상태(백그라운드/최소화 포함)와 시스템 알림 허용이 필요하다. 완전히 종료한 Mac 앱을 깨우는 기능은 추가하지 않았다. Android는 기존 FCM 등록과 시스템 알림 허용이 필요하다. 원격 알림 수신 여부와 상관없이 미확인 보고는 홈에 남는다.

결과 답글 전송은 독립적인 잠금/재시도 대기열을 사용한다. 전송이 실패해도 이미 완료된 일을 다시 실행하지 않는다. Google 요청 ID와 메시지 ID를 안정적으로 재사용해 네트워크 재시도 시 중복 전송을 줄인다.

## 새 업무 수집과 분리

등록된 예약 스레드의 대화와 완료 명령은 일반 신규 업무 분석으로 보내지 않는다. OS 자신의 예약 알림은 저장된 전송 번호와 회사 Google 사용자 ID를 함께 확인해 제외한다. 단순히 ‘예약’이라는 단어가 들어갔다고 다른 업무를 버리지 않는다.

제외한 답글도 수집 커서에는 반영해 같은 글을 계속 불러오지 않게 한다. 처리 실패가 있으면 완료 명령을 넘겨 커서를 진행하지 않는다. 재수집돼도 Google 메시지 ID 기준으로 중복 처리를 막는다.

알림 전송 응답 저장 전에 작성된 답글도 빠지지 않게, 새로 전송을 확정한 알림 스레드는 일반 수집 커서와 별도로 한 번 더 조회한다. 조회나 처리가 실패하면 확인 완료 표시를 남기지 않고 재시도한다. 오래된 알림이라고 임의로 완료 기능을 끄지는 않으며, 현재 연결·담당자·일감 버전으로 판단한다.

## 데이터 구조 및 배포

Schema 64는 외부 메시지/스레드 이름 nullable 열과 완료 명령·피드백 영수증 테이블을 추가한다. Schema 65는 완료 보고/확인 기록, 일감별 하나의 대기 보고 제약과 알림 종류를 추가한다. 기존 일감·연결·예약은 변경하지 않는다. 앞서 미배포 상태였던 Chat 앱 전용 코드는 폐기했으며 서비스 계정/공개 콜백 overlay도 제거했다.

`bash scripts/test-scheduled-chat.sh`는 격리 PostgreSQL에서 63→65와 기존 예약 회귀를 검사한다. 운영 스키마는 이 작업에서 변경하지 않는다.

배포 전에 백업을 확보한다. 서버/schema 65를 먼저 적용하고 화면과 네이티브 클라이언트를 갱신한다. Android 새 알림 종류의 클릭 이동은 신규 클라이언트가 필요하다. 장애 시 옵션을 끄거나 예약을 정지해 새로운 명령 수신을 중단할 수 있다. schema 63/64 바이너리는 65 DB의 readiness를 통과하지 않으므로 이미지 단독 downgrade 대신 확인 대기를 보존하는 호환 복구 바이너리 또는 승인된 백업 복구 절차를 사용한다. 완료·감사 기록을 임의 삭제하지 않는다.

실제 운영 계정에서 시험할 때는 전용 테스트 예약과 할 일을 사용해 전송자, 담당자 식별, 빈/입력 답글, 처리 결과 답글, 원본 CS/Redmine 외부 반영을 확인한다. 개발의 모의 Google 응답·DB 성공을 실제 Google 전송 성공으로 간주하지 않는다.
